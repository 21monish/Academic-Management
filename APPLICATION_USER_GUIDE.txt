GTU-ITR Academic Management System - Application User Guide
===========================================================

Last updated: 13 July 2026

Project folder:
C:\xampp\htdocs\GTU-ITR

Default local URL:
http://localhost:8000


1. What This Application Does
-----------------------------

GTU-ITR is a Laravel academic management system for institution setup,
academic masters, staff, students, attendance, exams, fees, leave, notices,
reports, user accounts, direct permissions, dashboards, chatbot support, and
campus automation.

The application is permission-aware. After login, users see only the menu items,
dashboard cards, records, and actions allowed by their role, direct permissions,
and hierarchy scope.

The main hierarchy is:

1. University
2. College
3. Department
4. Programme
5. Semester
6. Subject
7. Staff and Students


2. Starting The Application Locally
-----------------------------------

Before opening the app:

1. Start XAMPP.
2. Start Apache.
3. Start MySQL.
4. Confirm the database exists:
   gtu_itr

From the project folder, run:

php artisan serve

Then open:

http://localhost:8000

The public pages are available before login:

- /
- /features
- /modules
- /about
- /contact
- /login

Important:
MySQL must be running for login, dashboards, and every data screen. The local
configuration uses file sessions and file cache, but users, permissions,
students, fees, exams, notices, and other records are stored in MySQL.

5. Login, Logout, And Password Change
-------------------------------------

Login:

1. Open http://localhost:8000/login.
2. Select login type:
   Administration, Staff, or Student.
3. Enter username or email.
4. Enter password.
5. Sign in.

Login type rules:

- Administration checks administrator-style accounts created from
  Institution > Users.
- Staff checks linked staff accounts created from People > Staff.
- Student checks linked student accounts created from People > Students.

Staff and Student users should not be manually created from Institution > Users.
Create the Staff or Student record first; the system creates the linked login
account automatically.

Logout:

1. Use Exit or Log Out from the sidebar or mobile menu.
2. The app ends your session and returns you to the public area.

Forced password change:

If "must change password" is enabled on your account, the sidebar only shows
Change Password until the password is updated. The account needs
password_change.view and password_change.update permissions to complete this.


6. Main Screen Layout
---------------------

After login, the application shows:

- A desktop sidebar.
- A mobile menu on smaller screens.
- Role and email information.
- A direct Dashboard link.
- Permission-based module sections shown as dropdowns.
- Profile link when profile.view is allowed.
- Exit or Log Out button.

Navigation behavior:

- Home/Dashboard is a direct link, not a dropdown.
- Institution, People, Academic, Attendance, Exams, Fees, Leave, Notices,
  Reports, and System are dropdown sections.
- On desktop, moving the mouse over a dropdown opens it.
- Dropdowns have a smooth open animation.
- The current active section stays open automatically.
- On mobile, tap the menu button, then tap a section to open its links.

Branding is dynamic:

- Super Admin uses the global/system application name and logo.
- Other users use their assigned university name and logo when available.
- If a non-Super Admin user has no university logo, global branding from
  System Settings is used as a fallback.
- The browser tab title and favicon follow the same rule.

If a menu item is missing, the usual causes are:

- The user does not have the required permission.
- The user's hierarchy scope excludes that data.
- The user must change their password first.
- The route/module is not available to that account type.


7. Dashboards
-------------

The dashboard is role-aware and permission-aware.

General dashboards can show:

- Campus snapshot metrics.
- Quick links filtered by permissions.
- Analytics cards and charts.
- Recent notices in the user's scope.
- Recent activity if activity_log.view is allowed.
- One-click automation buttons when the user has the required permissions.

Student dashboard can show:

- Student profile summary.
- Enrollment number, programme, semester, academic year, college, and status.
- Attendance health.
- Fee balance and paid amount.
- Subject-wise attendance summaries.
- Results.
- Fee ledgers.
- Recent notices.
- Student quick links.

If a student login opens the student dashboard but no student profile appears,
the user account is active but not linked to a student record. An administrator
should connect the user to the correct student record or recreate the student
login with the correct programme/reference.


8. Roles, Permissions, And Scope
--------------------------------

The current seeded system roles are:

- Super Admin
- Admin
- Student

Legacy/common operational role names may exist or be created as institution
roles:

- University Admin
- Principal
- HOD
- Teaching Staff
- Non-Teaching Staff
- Accountant

Important permission rule:
Roles classify users, help set hierarchy, and can carry default permissions,
but the application also supports direct model-wise user permissions. If a user
can log in but cannot see a menu or perform an action, edit that user and grant
the exact permission needed.

Permission format:

module.action

Examples:

- dashboard.view
- university.view
- college.create
- department.update
- user_permission.update
- programme.view
- staff_assignment.create
- lecture.update
- marks_entry.update
- fee_collection.create
- notice.approve
- system_settings.update

Common action meanings:

- view: open the page and read records.
- create: add records or run create actions.
- update: edit, activate, deactivate, or modify records.
- delete: delete where the screen allows deletion.
- approve: approve or publish workflows where supported.
- ask: ask the chatbot.
- teach: add chatbot knowledge where enabled.

Hierarchy scope:

- Super Admin can work system-wide.
- Admin / University Admin is normally university-scoped.
- Principal is normally college-scoped.
- HOD is normally department/programme-scoped.
- Teaching Staff is normally staff/subject/semester-scoped.
- Student is normally own profile/programme-scoped.

The app infers scope from user fields and linked staff/student records:

- university_id
- college_id
- dept_id
- programme_id
- reference_type and reference_id
- staff email match when reference is not set
- active teaching staff subject assignments


9. User And Role Management
---------------------------

Menu:

Institution > Users
Institution > Roles

Create or edit a role:

1. Open Institution > Roles.
2. Add or edit a role.
3. Enter role name, description, university if applicable, staff type if this
   role is for staff, and active status.
4. Save.

Staff type on roles:

- Use Teaching for teaching roles such as Professor, Associate Professor,
  Assistant Professor, Lecturer, Visiting Faculty, or Lab Instructor.
- Use Non-Teaching for operational roles such as Clerk, Lab Assistant,
  Librarian, Accountant, Transport Staff, or other office/support roles.
- Use Both when the same role can be selected for either teaching or
  non-teaching staff.
- Staff creation uses this value to show only matching backend role options.

Create or edit a user:

1. Open Institution > Users.
2. Add or edit a user.
3. Enter username, email, phone, password if needed, role, and scope fields.
4. Set Active and Verified status.
5. Enable Force Password Change for new/manual accounts when appropriate.
6. Assign direct permissions in the User Permissions section.
7. Save.

Use Institution > Users for Administration accounts and for adjusting existing
permissions/status. Do not manually create Staff or Student login accounts here;
create staff from People > Staff and students from People > Students so the
profile and login stay linked correctly.

User fields:

- Username: login name, such as admin, hod.ce, faculty.ce, or student.1001.
- Email: must be unique.
- Role: controls dashboard type and common hierarchy behavior.
- University: required for university-level accounts.
- College: useful for principal, accountant, and college staff.
- Department: required for many HOD and department-level accounts.
- Programme: required for student accounts and programme-scoped users.
- Phone: optional contact number.
- Password: required for new users; leave blank when editing unless changing it.
- Active: inactive users cannot log in.
- Verified: usually checked for manually created internal accounts.
- Force Password Change: makes the user update password on next login.
- Direct permissions: exact page/action permissions for this user.

Deactivate instead of delete when the user is connected to historic payments,
marks, notices, attendance, or activity logs.

11. Institution Module
----------------------

Menu:

Institution > Universities
Institution > Colleges
Institution > Departments
Institution > Users
Institution > Roles

Universities:

Use this to manage university master records. Supported data includes name,
address, phone, email, website, established date, logo upload/path, UPI ID,
UPI name, UPI note prefix, and theme. University logo/branding can appear in
the sidebar for users scoped to that university.

Colleges:

Use this to create colleges under a university. Typical fields include code,
name, address, phone, email, principal name, affiliation type, college type,
affiliated date, and active status.

Departments:

Use this to create departments under a college. Typical fields include code,
name, description, HOD staff ID, and active status.

Users:

Use this to create login accounts, assign roles, choose hierarchy scope,
activate/deactivate accounts, force password changes, and grant direct
permissions.

Roles:

Use this to create and maintain role names. Access is ultimately enforced
through permissions attached to roles and/or directly to users.


12. People Module
-----------------

Menu:

People > Staff
People > Subject Assignments
People > Students
People > People Categories

Staff:

1. Open People > Staff.
2. Add Staff.
3. Select college and department.
4. Enter employee code, name, gender, date of birth, phone, email, address,
   photo, staff type, role, employment type, joining date, and active status.
5. Select Staff Type:
   Teaching, Non-Teaching, or Both.
6. Select Role.
   The role dropdown comes from Institution > Roles and is
   filtered by the selected staff type.
7. Select Employment Type:
   Permanent, Contractual, or Visiting.
8. For Teaching staff, enter qualification, specialization, designation,
   experience, and research details where available.
9. For Non-Teaching staff, enter role, section, and grade where available.
10. Save.

When staff is saved with an email, the system automatically creates or updates
the linked Staff login user. The username is the employee code. The first
password is the date of birth in ddmmyyyy format when date of birth exists;
otherwise the employee code is used. The generated user is forced to change
password on first login. After saving, the success message shows the generated
username and first password.

Students:

1. Open People > Students.
2. Add Student.
3. Select college, programme, category, and academic/admission details.
4. Enter enrollment number, first name, last name, gender, date of birth,
   contact details, guardian details, address, admission date, admission type,
   photo, and active status.
5. Save.
6. Open the student record to manage enrollments and elective choices.
7. The system automatically creates or updates the linked Student login account.
   The username is the enrollment number. The first password is the student's
   date of birth in ddmmyyyy format, and the student must change it on first
   login.

People Categories:

Use this for categories such as General, EWS, SC, ST, OBC, TFWS, Management,
or other local admission/student categories.

Subject Assignments:

This is the same staff assignment workflow also available under Attendance.
It connects teaching staff with subject, semester, college, lecture type, and
academic year.


13. Academic Module
-------------------

Menu:

Academic > Academic Years
Academic > Programmes
Academic > Semesters
Academic > Subjects
Academic > Curriculum
Academic > Elective Groups

Academic Years:

Create academic sessions such as 2026-27. Mark the current year as active when
needed.

Programmes:

Create degree programmes such as B.E. Computer Engineering or M.E. Computer
Engineering. Programmes belong to departments and include code, name, level,
duration in semesters, total credits, and active status. The programme screen
supports listing, filtering, sorting, viewing, creating, editing, deleting,
activating, and deactivating where permissions allow.

Semesters:

Create semesters under programmes. Semesters can be activated or deactivated.

Subjects:

Create subjects under departments. Typical fields include subject code, name,
type, category, credits, theory/lab/tutorial hours, elective status, and active
status. Subjects can be activated or deactivated.

Curriculum:

Map subjects to programmes and semesters. This determines which subjects are
available for a programme/semester.

Elective Groups:

Create elective groups and attach elective subjects so students can choose from
available options.


14. Attendance Module
---------------------

Menu:

Attendance > Teaching Staff Subject Assignments
Attendance > Timetable Slots
Attendance > Lectures
Attendance > Attendance Summary
Attendance > Defaulters

Typical workflow:

1. Create Staff Assignments.
   Assign staff to subject, semester, college, lecture type, and academic year.

2. Create Timetable Slots.

Teaching staff visibility:

staff subject assignments. If assignments are missing, confirm the staff record
email/reference and assignment status.


15. Exams Module
----------------

Menu:

Exams > Exams
Exams > Exam Subjects
Exams > Grade Master
Exams > Marks Entry
Exams > Results
Exams > Backlogs
Exams > Promotions

Exams > Hall Tickets
Exams > Exam Rooms
Exams > Seating

Theory exam workflow:

1. Create Exam.
   Select college, academic year, semester, exam type, start date, end date,
   and published status.

2. Add Exam Subjects.
   Attach subjects to the exam and set exam date, time, maximum marks, and

   Define grade letters, percentage ranges, grade points, and descriptions.

4. Enter Marks.
   Select exam subject, load students, enter theory/practical/internal marks,
   and save.

5. Review Results.
   View generated result rows, status, SGPA/CGPA summaries where available,
   and publication status.

6. Track Backlogs.
   Record and review failed or ATKT subjects.

7. Manage Promotions.
   Create or approve promotion decisions based on result and attendance data.

Exam logistics workflow:

1. Hall Ticket Config:
   Configure issue dates, minimum attendance percentage, fee clearance
   requirement, signatures, seal, instructions, and active status.

2. Hall Tickets:
   Generate or recheck hall tickets for eligible students.

3. Exam Rooms:
   Create rooms with room number, building, floor, capacity, type, and status.

4. Seating:
   Assign students to schedules, rooms, seats, and hall tickets.

5. Invigilators:
   Assign staff to exam rooms or schedules.

Practical workflow:

1. Create Practical Schedule.
2. Create Practical Batches.
3. Add students to batches.
4. Enter Practical Marks.

23. Dashboard Automations
-------------------------

Authorized users may see one-click automation buttons on the dashboard.

Available tasks can include:

- Run All Automations
- Backup System
- Generate ID Cards
- Refresh Attendance
- Send Fee Reminders
- Generate Timetable
- Refresh Dashboard
- Clear Fee Ledgers
- Generate Hall Tickets
- Publish Results
- Promote Students
- Publish Notices

Each automation appears only when the user has one of its required permissions.

Examples:

- Backup System needs high-level system/settings permissions.
- Generate ID Cards needs student report/student view permissions.
- Refresh Attendance needs attendance summary/report permissions.
- Fee Reminders need ledger/report/notice permissions.

----------------------------

3. Change the password.

Create a University Admin:

3. Set department HOD staff ID if applicable.
4. Create user with HOD role and Department scope.
5. Grant department/programme/student/staff/attendance/exam/notice permissions.

5. Edit generated user permissions if needed.

Create Non-Teaching Staff:

1. Open People > Staff.

3. Save and let the system create/link the user.

Create an Accountant:

3. Grant fee_category, fee_structure, student_ledger, fee_collection, receipt,

8. Grant extra student-facing permissions such as dashboard.view, profile.view,

   attendance_summary.view, result.view, receipt.view, result_card.view, and

26. Common Problems And Fixes
-----------------------------

Problem:
SQLSTATE[HY000] [2002] No connection could be made because the target machine
actively refused it.

Meaning:
MySQL is not running or Laravel cannot connect to MySQL.

Fix:

1. Open XAMPP Control Panel.
2. Start MySQL.
3. Check .env:
   DB_CONNECTION=mysql
   DB_HOST=127.0.0.1
   DB_PORT=3306
   DB_DATABASE=gtu_itr
   DB_USERNAME=root
   DB_PASSWORD=
4. Run:
   php artisan config:clear
5. Refresh the page.

Problem:
Login page opens, but login fails with database error.

Meaning:
The users table cannot be read because MySQL is unavailable or migrations have
not run.

Fix:

1. Start MySQL.
2. Confirm gtu_itr exists.
3. Run:
   php artisan migrate
   php artisan db:seed

Problem:
Menu item is missing.

Meaning:
The account lacks the required permission, is scoped away from the data, or is
still forced to change password.

Fix:
Ask an administrator to edit the user and grant the required permission from:
Institution > Users

Problem:
403 Forbidden.

Meaning:
The user is logged in but does not have permission for that route/action.

Fix:
Grant the exact module.action permission required by the page.

Problem:
419 Page Expired.

Meaning:
The session expired or the CSRF token is stale.

Fix:
Refresh the page, log in again if needed, and submit the form again.

Problem:
Uploaded logo/photo does not appear.

Fix:

1. Confirm the file exists under public/uploads or the configured path.
2. Confirm the path stored in the database is public or starts with a valid URL.
3. Run storage link if the file is stored under storage/app/public:
   php artisan storage:link

Problem:
Teaching Staff cannot see assignments.

Fix:

1. Confirm the staff record email matches the user email or user reference.
2. Confirm staff_assignment records are active.
3. Confirm the user has staff_assignment.view.
4. Confirm the staff member is assigned to the relevant subject and semester.

28. Safe Usage Tips
-------------------

- Change the default Super Admin password immediately.
- Keep Super Admin access limited to trusted administrators.
- Enter master data before dependent records.
- Do not delete records already used in payments, marks, attendance, reports,
  or notices unless you understand the consequences.
- Prefer deactivate where available.
- Back up the MySQL database before large imports or destructive changes.
- Review permissions after creating each operational user.
- Confirm scope fields when users report missing data.
